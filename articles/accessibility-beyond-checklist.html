Accessibility testing beyond the checklist

Accessibility By Kishore Gupta · 7 min read

Run an automated accessibility scanner over almost any web app and you'll get a tidy list of violations: missing labels, low-contrast text, images without alt attributes. Fix them all and the tool turns green. It's a satisfying moment — and a misleading one, because automated checks catch only a fraction of what actually stands between a person and your product.

Having led accessibility testing on enterprise healthcare applications — the kind where a blocked screen genuinely stops someone from getting care — I've learned to treat the automated pass as the starting line, not the finish.

What the tools do well

Automated checks are excellent at the objective, machine-verifiable rules: contrast ratios, missing form labels, invalid ARIA, duplicate IDs, tab order that's structurally broken. Run them in CI and they'll stop a whole class of regressions before code review. You should absolutely automate this layer — it's fast, consistent, and free.

Where they go quiet

The gap is everything that requires judgment. A tool can confirm an image has alt text; it cannot tell you the alt text says image123.png. It can confirm a button has an accessible name; it cannot tell you that name is "Click here" three times on the same page. Meaning is not machine-checkable.

  • Is the alt text actually useful, or just present?
  • Does the focus order tell a coherent story when you can't see the layout?
  • Do error messages announce themselves, or do they appear silently for a sighted user only?
  • Can you complete the core task — not just reach the controls — using only a keyboard and a screen reader?

Testing the way people actually use it

This is where structured manual testing earns its place. Working through the AVT levels — from basic conformance to full assistive-technology validation — means putting the app through the same tools real users rely on. Turning off the monitor and driving a whole workflow with a screen reader is humbling the first time. Menus that "looked accessible" turn out to trap focus. A confirmation that flashed on screen never reaches the audio channel.

Accessibility isn't a property you verify. It's an experience you have to live through.

None of this replaces automation. The two are complementary: let the machines guard the objective rules on every commit, and spend human attention on the judgment calls they can't make. A checklist tells you the door has a handle. Only a person can tell you whether someone can actually walk through it.

The mindset that matters

For teams building for accessibility, my advice is simple: automate the measurable, and never let the green checkmark convince you the work is done. Quality — accessibility included — is a mindset, not a phase. The people on the other side of the screen are counting on us to test for the experience, not just the rules.
